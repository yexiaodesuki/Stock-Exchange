# 模拟 USD 入金

登录交易页后点击“模拟入金 / 入金记录”。注册不自动配资；新用户与已有用户均可主动增加模拟 USD，不赠送股票、不覆盖原余额和冻结、不重置历史。没有卖方流动性时买单不会因为充值而自动成交。

## 配置和初始化

`config-repo/securities-api.yml` 显式开启本地模拟入金，默认单笔 1.00～100000.00 USD，每用户每日累计 500000.00 USD；日界线为 UTC，待确认申请也占额度。`SECURITIES_DEPOSITS_ENABLED=false` 禁止新申请，但已有申请继续处理、可查询和同键重试。配置经 Config Server 读取，修改后重启 API 生效；真实部署必须关闭，本功能不能替代银行、支付渠道或经纪商入金。

V5 由既有 Flyway 自动创建 `deposit_requests`、`deposit_daily_limits`、`deposit_outbox`。不需要手动执行 SQL、清库、删除容器或数据卷。既有 V1～V4 不修改。回退旧应用前应先停止新申请并确认所有 PENDING；不要删除迁移历史或入金记录。

## 请求与确认

浏览器 → Nginx → UI（Session、CSRF、本人签名）→ API。POST `/api/v1/deposits` 仅接受金额字符串和 `Idempotency-Key`；服务端身份不可由请求体覆盖。GET 同一路径按 `page=0&limit=20` 查询本人记录，GET `/{UUID}` 查询单条，GET `/policy` 读取非敏感限额。

登记事务锁住用户当日额度，同时保存申请和发件箱；同一用户同一键同金额返回原记录，不同金额返回 409。超额返回 429，参数错误返回 400，未登录返回 401，缺 CSRF 返回 403，读取他人记录返回 404。数据库故障和网络超时可能无法确认事务是否提交，客户端必须保留原金额和键。

后台每秒检查到期发件箱，每轮最多 50 条，领取后至少等待 5 秒再次处理。命令固定为 `CreditCash(USD, amount)`，唯一事件标识固定为 `deposit:{UUID}`，投递至原 transfer Topic，由定序持久化，再由引擎记账。发送/确认故障保留 PENDING；投递可能重复，依靠事件日志的同内容幂等，而不是声称 Kafka 天然恰好一次。API 或 Kafka 停机时不依赖用户重新点击来续跑。

仅持久执行结果存在且引擎报告已应用该序号，才更新 SUCCEEDED 或 REJECTED。结果存在但内存安装落后时继续等待。明确拒绝只释放一次原日期额度；超时不释放。SUCCEEDED 是持久入账确认，不是银行到账，也不是对引擎随后持续可用的承诺。

资金仍由原引擎、快照和事件恢复；`transfer_logs` 是成功流水，申请表不是新余额表，Redis 不作为入金权威状态。重放不再发旧通知，页面确认到账后读取权威账户，不在浏览器直接给余额加数。

页面在 sessionStorage 按用户暂存原金额、键和编号；刷新继续查询，提交响应丢失仍同键重试。关闭标签或换浏览器可能丢失尚未收到编号的本地暂存；服务端已受理申请仍继续处理，可从本人记录查询。分页是实时列表的 offset 分页，新记录到达时刷新首页，非固定审计快照。

## 验证

2026-10-30 最终完整 `-Gateway` 回归实际通过：Java 106 项，105 通过、1 项条件跳过，失败和错误为零；前端纯逻辑 6 项通过。真实浏览器验证老用户入金、响应丢失后刷新不重复到账、浏览器无法保存幂等键时不发送；真实进程验证新用户入金、越权拒绝、引擎强杀恢复和 API 重启自动续跑。不是公网安全评估或高并发压测。

入金记录仅包含此入口产生的申请；原演示初始化资金仍保留原流水，不伪造或回填成新的充值申请。

`node --test ui/src/test/js/domain.test.mjs` 验证前端纯逻辑。

`pwsh -File build/securities/test-phase2.ps1 -TestPattern 'DepositPolicyTest,DepositIntegrationTest,SecuritiesWebTest'` 在随机隔离库验证金额、事务回滚、并发额度、同键重试、发送故障、重复投递、结果安装延迟和隔离读取。

`pwsh -File build/securities/test-phase4.ps1 -Gateway` 运行全量隔离回归，增加真实 UI/API/Kafka/引擎入金、引擎强杀及 API 重启续跑，并在真实浏览器验证老用户入金和丢响应刷新幂等。开发用户不提交测试交易、不领取测试入金。

不包含真实支付、提现、股票转入、管理员审核、分布式事务或生产级吞吐承诺。持续故障可能长期 PENDING，应检查依赖和发件箱，不直接改余额或人工换键补发。
