# 一致性快照：初始化、启动和验证

## 适用范围与前提

快照保存在 MySQL `exchange.engine_snapshots` 表。日常重启保留用户、事件、历史订单和成交数据。只支持单交易引擎实例；当前实现不删除事件或快照、不补齐历史行情和异步投影。

全新安装时，Docker 在空 MySQL 数据目录中执行 `build/sql/schema.sql`，一次建立全部业务表和快照表。Java 应用不执行建表；空库首次启动会自动保存零序号初始快照。缺表、读库失败或首次快照保存失败会阻止启动就绪，不能当成“没有快照”忽略。

只启动一个交易引擎，并定期备份 `exchange` 数据库。备份保存在仓库外，避免把用户和账户数据上传到 GitHub。

## 一、首次安装一次建表

在项目 `build` 目录执行：

```powershell
docker compose -p stock-exchange up -d
docker compose -p stock-exchange ps
```

确认三个组件均健康。空 MySQL 数据目录会触发完整建表，不需要额外补表。`schema.sql` 包含 `DROP DATABASE`，禁止在日常重启时重新执行，否则会删除已有数据。

以下示例假设容器名为 `mysql`、数据库名为 `exchange`；使用不同名称时替换。PowerShell 在项目根目录执行：

```powershell
docker exec -it mysql mysql -uroot -p
```

在密码提示中输入本机配置的密码，不把密码写进命令或文档。在 MySQL 客户端执行：

```sql
USE exchange;
SHOW TABLES;
SHOW CREATE TABLE engine_snapshots;
SELECT COUNT(*) FROM engine_snapshots;
```

全新初始化后、引擎尚未启动时，快照行数应为 0。初始化脚本只负责创建结构，不充值、不插入快照；第一份快照由引擎自动生成。

Docker 初始化脚本只在空数据库数据目录首次初始化时执行。已有数据目录会被保留，重启不会重复建表。发现缺表时先核对容器挂载和首次初始化日志，不要对已有业务库重新执行删库脚本。

## 二、第一份快照由程序自动生成

保持 MySQL、Redis、Kafka 和 Config Server 可用，运行 `TradingEngineApplication`。首次启动与后续重启都执行以下流程：

1. 捕获 MySQL 已提交事件的恢复上界。
2. 尝试最近五份不领先于上界的快照；无有效候选则全量重放。
3. 有快照时恢复资产和活动订单，再重放快照序号之后的事件。
4. 校验完整状态，自动保存恢复结果到快照表。
5. 刷新 Redis 当前盘口，启动消费者和输出线程，进入 READY。
6. 启动周期快照任务。

快照安装不调用下单、转账或撮合方法，不重复冻结或清算；旧 Tick、私人通知、HTTP 结果和历史入库任务不属于快照内容。

查看就绪状态：

```powershell
curl.exe -i http://localhost:8002/internal/status
```

成功返回 200，响应含 `"ready":true`。启动恢复期间返回 503；恢复失败会使启动失败，端口可能不可连接。实际恢复行为仍需在本机联调确认，本说明不是已完成联调的证明。

在 MySQL 中检查快照，不必把完整账户 JSON 复制到聊天或日志：

```sql
SELECT id, sequenceId, formatVersion, createdAt,
       OCTET_LENGTH(snapshotData) AS bytes,
       CHAR_LENGTH(checksum) AS checksumLength
FROM engine_snapshots
ORDER BY sequenceId DESC, id DESC
LIMIT 5;
```

应有快照记录，格式版本为 1，SHA-256 文本长度为 64。空库也能生成零序号快照，不会虚构用户资产。序号是引擎已经完整应用的事件位置，不是随意读取数据库最大序号填入。

## 三、周期保存与重复启动

配置 `config-repo/trading-engine.yml` 的 `exchange.snapshot.interval-ms` 默认 60000 毫秒，也可通过 `ENGINE_SNAPSHOT_INTERVAL_MS` 环境变量设置，必须大于 0。

按固定延迟串行检查，只有事件位置变化才写入；不保证刚好每 60 秒完成一份快照。复制和一致性校验占用引擎锁，JSON 编码及数据库写入在锁外。大量账户与订单可能增加暂停时间和内存占用。

同位置、同版本、相同内容的有效快照不重复插入。损坏旧记录保留，允许追加新的完整记录；同位置已存在不同有效内容会报错，需排查时区、代码或状态变化，不擅自覆盖。

周期保存失败记录错误且不推进成功保存位置，下轮继续重试；运行中的引擎不因此自动清空或重启。此时必须保留事件历史，并关注日志，不能把周期失败视为无风险。

## 四、恢复验证建议（由用户或第四阶段执行）

自动化回归：

```powershell
mvn -o -f build/pom.xml test
```

离线依赖不齐时去掉 `-o`。快照测试使用 JDBC、消息和实时启动替身，不连接 Docker；测试证明算法、SQL 参数与边界，不证明真实 MySQL 事务、网络故障或断电持久性。

本机联调前先记录资产、冻结额和活动订单，保存一张不会立即成交的挂单。等待快照表的序号推进，暂停新交易，重启引擎；确认余额、冻结额、挂单及价格优先级一致，恢复后的挂单可以继续成交或撤单。日志应出现“已安装快照”，不要只依据 READY 判定恢复正确。

还应在隔离环境验证快照之后的增量事件、突然终止、写入失败和损坏回退。不要直接篡改当前业务库的快照、删事件或重置消费位置来做故障测试。

## 五、限制、失败与回退

- 格式版本不支持、文本校验失败或业务状态不一致：跳过候选，尝试旧候选；均无效时全量重放。候选只取最近五份，本阶段始终保留完整历史。
- 快照时区与引擎配置不同：阻止启动，避免改变订单 ID 的语义。
- 快照后的事件断链：阻止就绪，不以快照绕过顺序检查。
- 校验值只检测内容变化，不是防篡改认证；仍需限制数据库写权限。
- 快照和事件在同一个数据库，不替代数据库备份；MySQL 数据卷丢失可能两者一起丢失。
- 过大的 JSON 可能受 MySQL 数据包大小、查询耗时与 JVM 内存限制，应先测量再调整，不能仅凭 LONGTEXT 类型保证任意规模。
- 回退第二阶段代码可保留快照表，旧代码不读取它；不需要删除表、重新充值、清库或回退 Kafka 消费位置。

真实服务联调、快照保留策略、可靠异步输出与监控仍是后续工作，本阶段不宣称生产级资金安全。
